# 个人投资组合风险监控与决策辅助改进计划

日期：2026-09-07

状态：P0 数据监控基础设施已在本地实现并测试，待部署验收；P1–P3 待实施。具体行为与限制见 [P0 实现说明](portfolio-monitoring-p0.md)。

## 1. 目标与边界

在第一版确定性压力测试的基础上，把一次性情景计算升级为持续运行的个人组合风险监控：数据更新、风险计算、限额检查、危险信号、方案比较和事后复盘。

第一版模型说明见 [portfolio-stress-model.md](portfolio-stress-model.md)。保留已有的统一估值、时间戳、覆盖率、即时与单标的冲击、路径情景、共同测试资金及产品直接价格压力等设计。

系统回答三个问题：

1. 当前数据是否足以判断风险？
2. 在明确假设下，哪些持仓可能使我的损失超过个人限额？
3. 如果减仓或保留现金，风险和潜在收益会怎样变化？

不承诺预测市场、准确计算暴跌概率或保证避免损失；不自动交易。AI 负责解释，确定性引擎负责计算。未经用户确认，不把示例阈值当作个人投资规则。

## 2. 优先级与实施阶段

| 阶段 | 主要内容 | 完成标准 |
| --- | --- | --- |
| P0：可靠数据与估值口径 | VPS 后台协调刷新、价格来源与时间、现金与持仓口径、覆盖率、数据异常 | 不打开浏览器也能更新；过期或缺失数据不显示为安全 |
| P1：个人风险限额与预警 | 用户配置限额、组合及单标的风险、损失贡献、持续预警与恢复记录 | 每个预警能追溯输入、情景、计算版本和触发规则 |
| P2：可操作的方案比较 | 当前组合与减仓 25%/50%、退出至现金等方案比较 | 使用同一估值时点、同一账户资金及相同情景，展示成本与未知项 |
| P3：历史与校准 | 历史行情、日终快照、预警复盘、模型误差评估 | 能区分输入错误、模型误差与情景未覆盖，并跟踪误报与漏报 |

建议下一轮先实现 P0 与 P1 的最小闭环，再做 P2；无需先购买数据服务。

## 3. P0：让数据链路在 VPS 独立运行

### 3.1 后台刷新与计算

运行链路：持仓变更或定时任务 → 更新产品及标的行情 → 校验新鲜度 → 生成估值快照 → 运行压力测试 → 检查限额 → 保存预警与状态。

不再依赖打开“选股分析”页面来刷新压力测试使用的标的价格。复用现有 API、缓存、任务状态和调度设施；人工刷新与后台刷新应进入同一协调机制，避免重复请求。

建议频率是实施目标，不是对免费服务能力的保证：

- 标的行情：相关市场交易时段内每 1–5 分钟，优先复用现有 Alpaca；可按限额选择轮询或订阅。
- 结构化产品报价：初期保留现有约每小时刷新；确认提供方条款、限流和稳定性后，再对高风险仓位提频。
- 条款与 Greeks：每日检查，并在大幅价格变动、临近到期或障碍时按需刷新；记录其独立时间戳。
- 风险计算：输入更新后重算；即使没有新报价，也定期检查数据过期。
- 历史快照：至少日终保存一份；预警触发时保存完整输入。

按标的交易所、产品报价时段及障碍观察规则判断是否应更新，不能用单一 XETRA 日历代表所有产品。周末休市与交易时段刷新失败必须区分。

### 3.2 新鲜度与来源

每项输入记录产品标识、来源、币种、行情类型、市场时间、抓取时间和质量状态。市场时间未知时明确标为未知，不能把抓取时间冒充成交或报价时间。

检查产品报价、标的价格与 Greeks 的时间错位。风险信号旁显示所用输入的时间与缺失情况；数据不可靠时降低结果可信度或停止对应模型输出，不自动视为零风险。

数据异常与市场风险分别显示，例如“标的行情过期”和“压力损失超限”不能合并成一个模糊红灯。保留最后一次有效风险结果，但标注其时间和失效状态。

### 3.3 账户口径与全持仓覆盖

- 先核对现有“总资产”是否只是持仓市值；未纳入现金时，不把它称为完整账户 NAV。
- 核对数量、价格、币种、现金、待结算款及其他负债的来源；缺少可靠现金数据时，明确只按持仓市值计算比例。
- 所有比例标明分母：完整账户净值、持仓市值、共同测试资金或已投入候选资金。
- 组合监控覆盖全部持仓，不只 Tier 1。Tier 1 可以作为精细模型优先级，不能成为其他持仓风险消失的理由。
- 缺少标的或 Greeks 的产品继续提供产品自身报价下跌压力，单列不可建模部分；不得把产品跌幅等同于标的跌幅。
- 真实收益和回撤计算需处理入金、出金与持仓变动，不能直接把账户金额变化当作投资收益。

## 4. P1：个人风险规则与危险信号

### 4.1 用户可配置的风险预算

实施时需要用户确认以下设置，支持未设置状态，不默认宣称符合个人风险偏好：

- 最大可承受损失金额与回撤。
- 指定情景下的最大损失金额及占账户比例。
- 单标的、行业和发行人集中度上限；同一标的的不同产品合并展示。
- 杠杆或敏感度敞口上限，区分实时值、估算值和未知值。
- 障碍距离、到期窗口及最低现金缓冲。
- 最低模型覆盖率、可接受的数据时差和交易时段过期阈值。

示例：“标的同步下跌 10% 时，模型损失超过账户净值 5% 则提示”。这仅说明规则格式，不是推荐给用户的限额，也不是事件概率。

### 4.2 情景与贡献分析

保留同步冲击、单标的冲击和可配置幅度；逐步增加行业联合冲击、汇率变化与有明确来源的历史标的路径。

每个情景展示损失最大的持仓、按标的合并的贡献、未覆盖部分和现金。对 Factor 展示路径及重置假设；对 Knock-out 展示路径触及障碍的结果和实际条款限制。当前 Greeks 不能当作全幅度、全期限都有效的常数。

只具备当前报价时，可以运行确定性压力测试；不能据此构造可靠的历史损失分布、VaR 或收益概率。加入历史标的行情也不等于获得结构化产品的真实历史表现。

### 4.3 预警生命周期

一条预警至少包含：触发原因、影响持仓、数据时间与来源、情景、预计损失、个人限额、数据可信度及建议检查事项。

记录首次触发、最后触发、确认、恢复与失效状态。普通规则可通过连续命中、冷却时间和恢复阈值减少抖动；数据失效及明确的紧急风险单独设计规则，不能被普通去重机制隐藏。

首版采用应用内预警列表与日终摘要。后续是否使用邮件或其他通知渠道，由用户选择和授权；不默认连接外部服务或发送持仓信息。

## 5. P2：用于决策的方案比较

以真实当前持仓为起点，而不仅展示抽象的稳健、均衡、高弹性候选组合：

- 保持现状。
- 将某个持仓或同一标的敞口减仓 25% / 50%。
- 完全退出某持仓并保留现金。
- 仅在替代品有可用报价、条款和足够输入时，比较替代方案。

所有方案使用同一账户资金、估值时点和情景，展示交易后现金、压力损失、风险贡献变化、上行情景收益减少，以及费用、点差与税务影响是否计入。

未获取买卖报价时只能提供估值模拟，不称为可成交报价。不得用不具备数据的替代产品生成看似精确的买入数量或收益比较。

Hermes 只解释已算出的结果与假设，不自行修改阈值、补造行情或生成未经校验的损益数字。AI 返回格式无效时，确定性风险监控和预警必须继续工作。

## 6. 免费数据优先方案

以下是前期讨论所依据的官方来源；免费额度、许可和接口能力可能变化，实际接入前再次核验。免费不代表无限调用，也不代表可任意抓取或转发。

| 数据来源 | 用途 | 主要限制与处理 |
| --- | --- | --- |
| 现有 Alpaca 免费 Basic | 支持的美股/ETF 标的行情与历史数据 | 免费实时股票数据是 IEX 单市场，不是完整 SIP；此前查阅为 30 个 WebSocket 标的、历史请求 200 次/分钟，接入时复核 |
| Alpaca 历史 SIP | 延迟历史路径、日终复盘 | 免费历史访问需避开最近 15 分钟；不能理解为免费完整实时 SIP 或免费延迟推送 |
| 现有产品报价来源及发行人官方页面 | 产品报价、障碍、行权价、到期、重置与终止规则 | 优先复用现有链路；遵守条款、限流，缓存静态字段；网页抓取不视为稳定公共 API |
| 自己积累的产品行情快照 | 产品历史、模型校准与预警复盘 | 从开始保存之日起积累，无法补造过去行情；重复旧报价不能标作新行情 |
| Frankfurter | 每日汇率换算与历史汇率 | 日频参考汇率，不用于盘中可成交汇率或即时汇率预警 |
| 上市公司投资者关系页面 | 已确认的财报与重大事件日期 | 人工核验或合规低频采集；区分预计日期与已确认日期 |
| Alpha Vantage 免费层 | 少量低频补充数据 | 此前查阅标准免费额度为每日 25 次；不适合大量持仓的分钟轮询，部分功能需付费 |

## 7. P3：验证是否真正有用

先以观察模式运行，收集每次预警及后续实际报价变化，不直接驱动交易。复盘时区分：行情不新、字段或条款错误、模型近似误差、真实路径未被情景覆盖。

关注指标：

- 按市值统计的报价与标的模型覆盖率、交易时段新鲜度达标率。
- 风险计算到预警展示的延迟、任务失败与漏运行次数。
- 重复预警、用户确认或忽略情况、按预先定义标准统计的误报与漏报。
- 产品实际价格变化与模型近似的差异，按产品类型分组。
- 用户是否能从预警识别主要损失来源，以及方案比较是否清楚呈现风险与收益取舍。

不以“短期赚了钱”单独证明模型有效；不把当前持仓和当前 Greeks 套到历史行情的结果称为真实历史回测。

## 8. 验收清单

- [ ] 关闭浏览器后，VPS 仍按各市场时间更新与计算。
- [ ] 人工刷新与定时任务不会重复轰炸同一提供方；失败有退避和可见状态。
- [ ] 周末、节假日、盘后、未知时间和交易时段过期均有测试。
- [ ] 抓取时间与市场时间分开；旧产品报价配新标的价格有明确提示。
- [ ] 非 Tier 1 和不可建模持仓仍计入账户口径及未覆盖风险。
- [ ] 现金不完整时不冒用完整 NAV；不同方案使用同一分母。
- [ ] 缺少报价、标的、Greeks 或汇率不会静默变成零风险。
- [ ] 预警支持去重、冷却、恢复、输入追溯与配置版本记录。
- [ ] 阈值未配置时不宣称组合符合个人风险限制。
- [ ] 减仓方案守恒：保留持仓价值加现金与费用调整前后相符。
- [ ] AI 超时、不可用或格式错误不影响确定性监控。
- [ ] 历史数据无前视信息，快照可重放，模型版本可追溯。

## 9. 后续实施前需要确认

1. 账户是否有可靠现金及负债数据；缺失时采用何种明确标注的分母。
2. 用户个人损失预算、集中度与到期/障碍阈值。
3. 应用内以外是否需要通知，以及允许发送的信息范围。

这些选择不妨碍先实现后台数据协调、质量状态与快照基础设施。后续代码修改、VPS 部署和外部通知接入分别按用户授权推进。
